## 1. Executive Summary

### Краткое описание

**ra2-analog** — мультиплеерная игра про конструирование боевых роботов, проектирование системы управления, быстрое тестирование и физические бои. Игрок собирает машину из модулей, назначает действия на органы управления, проверяет гипотезы в тестовой комнате и выводит результат в арену.

### Жанр

Robot combat / sandbox construction / physics fighting с акцентом на engineering и control design. Долгосрочный фокус — **PvP**.

### Ключевая фантазия игрока

«Я — инженер, который придумал машину, сам написал ей „нервную систему“ управления, проверил её на стенде и вывел в бой против чужих конструкций.»

### Уникальность

Ценность игры — не каталог юнитов и не «скины с ХП», а **глубина инженерного конструирования** и **свобода проектирования управления**. Робот — физическая система; победа растёт из конструкции, схемы управления и навыка пилота.

### Целевая аудитория

- игроки, которым нравятся sandbox-конструкторы и физические песочницы;
- фанаты Robot Arena / подобного engineering combat;
- игроки, любящие «придумал → проверил → улучшил»;
- PvP-аудитория, готовая конкурировать навыком и дизайном, а не прогрессией силы.

### Чем отличается от обычных robot combat games

| Типичный robot combat | ra2-analog |
|----------------------|------------|
| Готовые шасси / пресеты | Свободная модульная сборка |
| Фиксированное управление | Игрок проектирует control scheme |
| Бой = цифры урона / abilities | Бой = физика, масса, соединения, отказы |
| Контент ради объёма | Компактный контент, глубокие системы |
| Мультиплеер «потом» | Multiplayer — core feature с дизайна |
| Прогрессия силы в PvP | Skill + engineering, экономика вне core MVP |

## 2. Design Pillars

1. **Engineering**  
   Игрок решает инженерные задачи: масса, мощность, прочность соединений, устойчивость, компоновка. Ошибки конструкции — часть геймплея, а не баг UX.

2. **Freedom of Construction**  
   Максимально широкое пространство решений внутри ясных физических и конструктивных правил. Нет «правильного» робота — есть гипотезы, которые проверяются в тесте и бою.

3. **Control Programming**  
   Управление — полноценный слой дизайна. Actions, bindings, groups и composite actions делают пилотирование продолжением инженерии.

4. **Physics**  
   Физика — не декорация, а язык взаимодействия: столкновения, крутящий момент, центр масс, отрыв деталей, поведение на арене.

5. **Fast Iteration**  
   Цикл «собрал → настроил → проверил → поправил» должен быть коротким и привычным. Долгие загрузки между Design / Configure / Test — антипаттерн.

6. **Multiplayer-first**  
   Игра проектируется как соревновательная/совместная среда. Локальный песочный опыт важен, но системы не должны предполагать «потом как-нибудь добавим сеть».

7. **Skill-based PvP**  
   В PvP преимущество дают конструкция, схема управления и навык. Не обязательный pay-to-win и не progression-based power advantage как основа баланса.

8. **Depth over Content Volume** *(дополнительный pillar)*  
   Лучше меньше типов деталей при богатых взаимодействиях, чем огромный каталог без системной глубины.

## 3. Player Experience

### Проектирование (Design)

Ощущение: «Я собираю машину с характером».  
Игрок думает о компоновке, устойчивости, где поставить оружие, хватит ли мощности, не развалится ли конструкция. Есть предвкушение: «это должно работать вот так».

### Настройка (Configure)

Ощущение: «Я оживаю машину нервами управления».  
Игрок назначает действия, собирает группы, придумывает схемы вроде танкового руления. Чувство авторства усиливается: робот уникален не только формой, но и тем, как им водят.

### Тестирование (Test)

Ощущение: «Я проверяю гипотезу, а не „запускаю уровень“».  
Быстрый заезд, обнаружение крена, нехватки тяги, кривого биндинга, слабого соединения. Минимум трения — максимум честной обратной связи от физики.

### Бой (Battle)

Ощущение: «Моя конструкция встречается с чужой реальностью».  
Напряжение, импровизация, использование сильных сторон машины, адаптация к повреждениям. Победа ощущается как заслуга дизайна и пилотажа.

### Анализ результатов (Results)

Ощущение: «Я понял, почему проиграл / выиграл».  
Статистика и факты боя превращаются в список гипотез для следующей итерации, а не в абстрактный score.

### Повторная итерация

Ощущение ядра опыта:

> **Я придумал конструкцию → проверил гипотезу → обнаружил проблему → изменил конструкцию → снова проверил.**

Этот цикл должен быть эмоциональным сердцем игры. Каждая «неудача» в Test или Battle — топливо для следующего Design, а не наказание. Игрок уходит с ощущением прогресса понимания своей машины, даже если счёт проигран.

Желаемый ритм сессии: короткие петли итерации в редакторе/тесте, затем осмысленный выход в бой, затем снова петля улучшений.

## 4. Core Gameplay Loop

```
DESIGN → CONFIGURE → TEST → BATTLE → RESULTS → DESIGN
              ↑_________________|
         (быстрые локальные петли Design ↔ Configure ↔ Test)
```

### DESIGN

| | |
|--|--|
| **Цель** | Создать физически осмысленную конструкцию робота |
| **Действия** | Задать корпус/границы, выбрать материалы, разместить компоненты, соединить, учесть массу/мощность |
| **Системы** | Construction, materials, components, constraints, mass/CoM preview |
| **Результат** | Черновик или готовая к настройке машина |
| **Переход** | В Configure (основной) или сразу в Test, если схема управления уже есть |

### CONFIGURE

| | |
|--|--|
| **Цель** | Сделать робота управляемым так, как задумал игрок |
| **Действия** | Назначить actions на ввод, создать groups, определить composite actions |
| **Системы** | Actions, bindings, groups, input mapping |
| **Результат** | Рабочая (или частично рабочая) схема управления |
| **Переход** | В Test для проверки; назад в Design при нехватке органов/мощности |

### TEST

| | |
|--|--|
| **Цель** | Быстро подтвердить или опровергнуть гипотезу о конструкции и управлении |
| **Действия** | Spawn, езда, стрельба, стресс-тесты, reset, правки на лету (через быстрый возврат) |
| **Системы** | Test room, physics sandbox, control debug aids |
| **Результат** | Список обнаруженных проблем / уверенность «готово к бою» |
| **Переход** | Назад в Design/Configure или вперёд в Battle |

### BATTLE

| | |
|--|--|
| **Цель** | Проверить робота против правил арены и другого игрока/роботов |
| **Действия** | Пилотирование, использование оружия, адаптация к повреждениям |
| **Системы** | Arena, match rules, damage, multiplayer session |
| **Результат** | Победа / поражение / иной исход по правилам матча |
| **Переход** | В Results |

### RESULTS

| | |
|--|--|
| **Цель** | Понять исход и получить материал для следующей итерации |
| **Действия** | Просмотр статистики, ключевых событий, причин поражения |
| **Системы** | Post-battle stats, (опционально) replay позже |
| **Результат** | Осмысленные выводы → новый Design |
| **Переход** | В Design (или снова в очередь на бой с той же машиной) |

## 5. DESIGN SYSTEM

### Концепция

Design — пространство, где игрок определяет **что** является роботом: геометрию, материалы, набор модулей и их связи. Все решения должны иметь последствия в физике и бою.

### Корпус и границы конструкции

- Игрок задаёт **границы/форму** корпуса (объём, в пределах которого строится машина).
- Границы ограничивают размещение и помогают читать силуэт/габариты.
- Точная модель редактора корпуса (воксели / поверхности / пресеты каркаса) — **open question**.

### Материалы

- Материалы влияют на массу, прочность, возможно трение/стоимость (если economy включена позже).
- В MVP достаточно различимого влияния на массу и живучесть.
- Богатая материаловедение — post-MVP / future.

### Компоненты

- Робот собирается из **компонентов** (двигатели, колёса, оружие, приводы, батареи и т.д.).
- Каждый компонент — экземпляр data-driven определения (см. §6).

### Размещение

- Игрок размещает компоненты в пространстве конструкции.
- Важны коллизии между деталями, доступность соединений, влияние на CoM.
- Снап/свободное размещение — open question на уровне UX, но свобода компоновки обязательна по духу.

### Соединения

- Компоненты **соединяются** друг с другом (жёстко / шарнирно / через приводы — по типу связи).
- Соединения определяют структуру, передачу сил и точки отказа при damage.

### Ограничения

Примеры классов ограничений (конкретные числа — не фиксируются здесь):

- габариты / лимиты арены или режима;
- максимальная масса (если режим задаёт);
- требования к питанию / суммарной мощности;
- недопустимые пересечения;
- лимиты на число определённых компонентов (режимные, не обязательно глобальные).

### Масса и центр масс

- Суммарная масса и **центр масс** — первоклассные параметры дизайна.
- Игрок должен иметь возможность видеть/чувствовать последствия смещения CoM (крен, переворот, нестабильность).

### Мощность

- Источники энергии/приводы ограничены; потребители (моторы, оружие) конкурируют за бюджет.
- Нехватка мощности — частая «гипотеза, которую ломает Test».

### Физические ограничения

- Нереалистичные «магические» крепления без последствий противоречат pillar Physics.
- Дизайн должен поощрять устойчивые, сбалансированные решения, не запрещая безумные эксперименты в sandbox/Test.

### Разделение по горизонтам

| Обязательно для MVP | После MVP | Future |
|---------------------|-----------|--------|
| Размещение базовых компонентов | Расширенные материалы | Продвинутый редактор корпуса |
| Базовые соединения (достаточные для езды/удара) | Больше типов joints/приводов | Процедурная прочность/усталость |
| Масса и читаемый CoM | Тонкая настройка инерции | Детальная аэродинамика и т.п. |
| Простые лимиты мощности | Сложные энергосети | Тепло / перегрев как система |
| Сборка, пригодная к Test и Battle | Режимные лимиты турниров | Командные «шасси-правила» |

## 6. COMPONENT SYSTEM

### Универсальный компонент

Компонент — единица конструкции и поведения. Добавление нового типа должно опираться на **данные и декларацию capabilities**, а не на уникальную ветку «всей игры».

### Модель свойств (дизайн-уровень)

| Аспект | Содержание |
|--------|------------|
| **Физические свойства** | Масса, размеры, коллизия, прочность, (опц.) трение, точки крепления |
| **Функциональные свойства** | Роль: движение, привод, оружие, энергия, структура… |
| **Входы** | Энергия, управляющие команды, сигналы от связанных частей |
| **Выходы** | Сила/крутящий момент, движение, снаряды/эффекты, статус |
| **Actions** | Дискретный набор действий, доступных Configure |
| **Ограничения** | Max скорость, угол, расход энергии, кулдауны (если нужны) |
| **Зависимости** | Требует батарею / опору / соединение определённого типа |
| **Состояние** | Intact / damaged / disabled / detached / destroyed (уточняется damage-моделью) |

### Примеры компонентов

**Колесо**  
Физика: контакт с поверхностью, трение, нагрузка.  
Actions: вперёд, назад, (опц.) steer.  
Зависимости: привод/мощность, крепление к корпусу.

**Ротор / мотор**  
Actions: вращение +, вращение −, стоп/фиксация, тормоз.  
Выход: крутящий момент на соединённый элемент.

**Поршень**  
Actions: выдвинуть, задвинуть, остановить.  
Использование: подвеска, щит, «толкатель», экзотические кинематические сборки.

**Оружие (простое)**  
Actions: activate / deactivate (или fire).  
Состояние: перегрев/боезапас — по необходимости горизонта.

**Батарея / источник энергии**  
Функция: бюджет мощности.  
Повреждение батареи → деградация всей машины.

**Структурный блок**  
Мало actions, много роли в массе, броне и топологии соединений.

Список стартовых компонентов для MVP должен быть **коротким, но достаточным** для езды, базового оружия и хотя бы одного «интересного» привода (ротор/поршень) — точный каталог open question.

## 7. CONTROL / CONFIGURATION SYSTEM

Одна из ключевых механик: игрок проектирует **систему управления**.

### Actions

- Атомарные команды компонента (`Wheel.Forward`, `Rotor.Brake`, `Gun.Fire`…).
- Имеют смысл только в контексте экземпляра или группы.

### Bindings

- Связь: **вход игрока → action** (или composite action).
- Bindings сохраняются вместе с роботом/пресетом управления.

### Groups

- Несколько компонентов объединяются в группу.
- Группа — единица назначения поведения (например, «левые колёса», «вся ходовая»).

### Composite actions

- Одно нажатие → набор действий по членам группы (возможно с разными знаками/режимами).
- Пример танкового руления на 4 колёсах:

| Ввод | Composite |
|------|-----------|
| W | все вперёд |
| S | все назад |
| A | левые назад + правые вперёд |
| D | левые вперёд + правые назад |

### Аналоговый и цифровой ввод

- Цифровой: on/off actions.
- Аналоговый: величина газа/поворота, если компонент это поддерживает.
- Какие устройства ввода в MVP (клавиатура / геймпад) — open question; принцип поддержки обоих желателен.

### Конфликты, приоритеты, одновременность

Дизайн должен определить политику (детали реализации — не здесь):

- два биндинга на одно действие;
- противоположные команды одной оси (W+S);
- одновременная активация движения и оружия;
- приоритет group composite vs прямой binding на член группы.

Пока фиксируется **требование**: поведение при конфликтах должно быть предсказуемым и объяснимым игроку (подсказки/отладка в Configure/Test).

### Примеры схем управления

1. **Классический драйв:** WASD = composite ходовой, ЛКМ = оружие.  
2. **Двойное назначение:** Q/E = поворот башни/ротора, Space = поршень-толкатель.  
3. **Экзотика:** одна кнопка = «сложить» кинематическую раму + активировать шип.

## 8. TEST ROOM

### Назначение

Безопасная песочница для проверки конструкции и управления **до** ставки рейтинга/матча. Главный инструмент цикла гипотез.

### Функциональность

- мгновенный (или почти мгновенный) вход из Design/Configure;
- управление роботом текущей схемой;
- наблюдение физики: устойчивость, тяга, прыжки, столкновения с препятствиями;
- проверка оружия и приводов;
- быстрый **reset** состояния робота и комнаты;
- **spawn** в стандартной/выбранной позе.

### Инструменты и aids (дизайн)

| Инструмент | Назначение |
|------------|------------|
| Reset | Вернуть робота в исходное состояние |
| Respawn / teleport | Сменить точку проверки |
| Пауза / замедление (желательно) | Разбор странного поведения |
| Подсветка активных actions | Отладка биндингов |
| Индикаторы мощности/массы/CoM | Связь с Design |
| Простые препятствия / рампы / стены | Стресс-тесты |
| Лог недавних ошибок управления (мягкий) | «Почему не едет» |

### Физические тесты и проверка управления

Игрок должен суметь за минуты ответить:

- едет ли машина прямо;
- не переворачивается ли;
- хватает ли мощности;
- работают ли composite actions;
- живут ли соединения под нагрузкой (в пределах MVP damage/physics).

### Бесшовный переход Design ↔ Configure ↔ Test

**Обязательное UX-требование:** эти три состояния — грани одного рабочего места, а не три «уровня с загрузкой».  
Допустимы короткие переключения сцены/режима, недопустимы традиционные долгие loading gates между правкой и проверкой.

## 9. BATTLE SYSTEM

### Условия начала

- Игроки (или локальные участники прототипа) готовы с валидными роботами.
- Выбран формат/правила матча (даже если в MVP формат один).
- Роботы заспавнены на арене по правилам режима.

### Правила (концепт)

- Бой физический: контакт, оружие, разрушение/отказы влияют на исход.
- Конкретный win condition зависит от формата (см. ниже).

### Победа / поражение / уничтожение

Возможные условия (не все обязательны сразу):

- уничтожение критических систем / «смерть» робота;
- elimination (выбыл — проиграл);
- набор очков урона за время;
- последний выживший;
- сдача / disconnect по правилам матча.

Точный набор win conditions для MVP — см. §17 и Open Questions.

### Damage в бою

Damage — часть боя, не отдельный мини-режим. Последствия должны читаться: робот слабеет, теряет функции, меняет поведение.

### Arena

- Пространство с коллизиями и достаточным местом для манёвра.
- Сложность арен (ловушки, движущиеся элементы) — не обязательна для MVP.

### Time limits

- Таймер матча желателен для PvP (защита от бесконечных клинчей).
- Что происходит по таймеру (урон за время, судьи по HP/функциональности) — open question.

### Возможные форматы PvP (не финальный список)

- 1v1;
- несколько роботов FFA;
- командные;
- турнирная сетка;
- elimination;
- timed battles.

**Окончательный набор режимов не фиксируется** этим документом.

## 10. DAMAGE SYSTEM

### Концепция

Повреждения меняют **функцию и физику** робота, а не только полоску HP. Идеал: попал в колесо — потерял мобильность; оторвал оружие — потерял огневую мощь; разрушил соединение — отвалился модуль.

### Слои повреждений

| Слой | Смысл |
|------|--------|
| Повреждение компонента | Снижение эффективности / прочности |
| Функциональное | Actions слабее/недоступны |
| Физическое разрушение | Отрыв, обломки, изменение массы/CoM |
| Отключение | Компонент disabled без обязательного отрыва |
| Потеря соединений | Топология машины меняется |
| Последствия | Каскадные отказы (нет энергии → всё глохнет) |

### Горизонты

| MVP | Post-MVP | Future |
|-----|----------|--------|
| Урон по компонентам с отключением ключевых функций | Частичная деградация (не только on/off) | Детальная локальная деформация |
| Базовое «уничтожен / выведен из строя» | Отрыв модулей с сохранением обломков | Усталость материалов, пожары и т.п. |
| Читаемая причина потери функции | Каскадные энерго-отказы | Детальный pen/armor model |

## 11. MULTIPLAYER

### Почему это core feature

Фантазия «мой робот против твоего» — социальное и соревновательное ядро жанра. Откладывание сети «на потом» обычно ломает архитектуру и дизайн систем (состояние робота, physics authority, damage events).

### Multiplayer-aware части игры

Должны проектироваться с учётом сети (на уровне дизайна данных и правил):

- определение робота (сборка + схема управления);
- состояние компонентов и повреждений;
- ввод / команды управления;
- физическое состояние в бою;
- правила матча, join/leave;
- результаты и античит-чувствительные исходы.

Design/Test могут быть локальными, но **формат сохранения робота** и **правила валидности** должны быть пригодны для передачи в матч.

### Какие данные концептуально синхронизируются

- идентичность и версия робота участника;
- команды управления (или авторитетный результат симуляции);
- состояние позы/скоростей (в рамках выбранной net-модели — без фиксации здесь);
- события урона / отрывов / уничтожения;
- фаза матча (lobby → countdown → fight → results).

### Создание и изменение робота

- Сборка и configure — до матча (и в Test).
- В бою массовый «ремонт/пересборка» обычно недоступны (исключения — отдельные experimental режимы).
- Смена робота между матчами — нормальный цикл.

### Путь в бой

Типичный поток: **готовая машина → lobby / очередь → арена → results**.

### Lobby

- Список игроков, статус готовности, выбранные роботы (или скрытые до старта — open question).
- Параметры матча, если не только matchmaking.

### Matchmaking

- Подбор по режиму; skill-based matchmaking — желателен позже.
- Для раннего мультиплеера допустим простой lobby/direct join.

### Disconnect / reconnect

- Правила: поражение, пауза, замена ботом, окно reconnect — **open**, но политика должна быть явной в режиме.
- Злоупотребление disconnect не должно награждаться.

### Spectator / replay

- Spectator и replay — ценны для обучения и комьюнити.
- Относятся к post-MVP / future, но желательно не проектировать лог боя так, чтобы replay стал невозможен навсегда.

### Ранний дизайн-риск (игровой)

Нужно рано проверить: **интересен ли физический бой двух машин онлайн**, даже на урезанном feature-set. Это product/design gate, не только технический.

## 12. RESULTS / POST-BATTLE

После боя игрок получает понятный разбор.

### Минимально полезный набор

- исход матча и причина (уничтожение, таймер, сдался…);
- нанесённый / полученный урон (в принятых единицах);
- какие компоненты получили критический ущерб / были уничтожены;
- длительность боя / время «эффективной активности».

### Расширенный набор (post-MVP+)

- эффективность оружия (попадания, uptime);
- энергия / мощность (если модель достаточно зрелая);
- мобильность (простой прокси: время в движении, перевороты);
- ключевые события таймлайна;
- сравнение с прошлыми боями того же робота (future).

Results должны **подталкивать** возврат в Design, а не только показывать рейтинг.

## 14. CAREER / ECONOMY

**Не входит в core gameplay loop MVP.**

### Возможный career loop (опциональный слой)

Заработок → покупка/разблокировка деталей → улучшение машины → участие в событиях/турнирах → новый заработок.

### Преимущества

- долгосрочная мотивация;
- структура «сезона»;
- онбординг через ограниченный стартовый набор.

### Риски

- pay-to-win / grind-to-win в PvP;
- сужение creative freedom;
- инфляция силы деталей;
- давление на балансировку каждого нового компонента через экономику, а не через физику.

### Влияние на PvP

Если economy включает силу, PvP перестаёт быть честным инженерным конкурсом.  
Безопасные варианты: косметика, отдельные casual ladder с restrictions, или идентичные unlock для всех в ranked.

### Вывод дизайна

Economy — **подключаемый слой**. Core фантазия должна работать в sandbox без денег.

| Вариант | Суть | Безопасность для PvP |
|---------|------|----------------------|
| **Skill-based** | Рейтинг, знание, механика пилота | Высокая |
| **Unlock-based** | Открытие деталей | Средняя/низкая, если unlock = сила |
| **Cosmetic** | Внешний вид без силы | Высокая |
| **Career** | Деньги/ресурсы | Рискованно без жёстких ограничений |
| **Sandbox** | Всё доступно для творчества | Высокая для fair fights (все на равных) |

**Рекомендация документа:** для соревновательного PvP опираться на skill + равный доступ к релевантному набору деталей (или явные ограниченные brackets). Unlock силы — только с отдельной политикой режимов.

## 16. UI/UX PRINCIPLES

1. **Минимум загрузок** между Design / Configure / Test.  
2. **Быстрый iteration loop** — правка и проверка в одном дыхании.  
3. **Понятные связи компонентов** — игрок видит, что с чем соединено.  
4. **Визуализация ошибок** — пересечения, нет питания, невалидный биндинг.  
5. **Визуализация управления** — что делает клавиша / какие части сейчас активны.  
6. **Понятная обратная связь** в бою и тесте — почему отвалилось, почему не едет.  
7. **Честность физики** — UI не врёт о массе, мощности и повреждениях.  
8. **Сложность систем ≠ сложность первого шага** — онбординг может ограничивать UI, не фантазию.

## 17. MVP DEFINITION

MVP — уже **настоящий Robot Arena-like продукт**, а не только редактор.

### Игрок в MVP должен уметь

1. Собрать робота из небольшого набора компонентов с массой, соединениями и бюджетом мощности.  
2. Настроить управление: actions + хотя бы groups/composite для ходовой.  
3. Мгновенно (по ощущению) гонять машину в Test Room, reset, править, повторять.  
4. Вывести двух роботов в физический бой с читаемым исходом (уничтожение / неработоспособность / таймер — выбрать одно ясное правило).  
5. Увидеть базовые results и вернуться в Design.  
6. Иметь задел multiplayer-aware: даже если онлайн хрупкий, путь «два игрока → бой» проверяет главный риск жанра.

### MVP не обязан иметь

- богатую экономику и карьеру;
- большой каталог деталей;
- полный набор PvP-режимов;
- spectator/replay;
- сложную деградацию damage;
- финальный выбор всех чисел баланса.

## 18. OUT OF SCOPE (ранний этап)

- Pay-to-win / battle pass силы.  
- Огромный контентный каталог «ради галочки».  
- Кинематографичный синглплеер-кампейн как замена core loop.  
- Финальный набор турнирных форматов.  
- Глубокая экономика как обязательный слой.  
- Полировка всех edge-case анимаций/VFX до проверки physics+PvP.  
- Смена production engine (Unity зафиксирован; Unreal и др. вне scope).  
- Финальный выбор Unity packages без экспериментальной валидации.  
- Сложный meta-progression, ломающий fair fights.

## 20. DESIGN RISKS

| Риск | Причина | Последствия | Способ проверки |
|------|---------|-------------|-----------------|
| Iteration loop слишком медленный | Загрузки / разрозненные режимы | Игрок бросает инженерию | Замер времени Design→Test на прототипе UX |
| Control system слишком сложен | Много сущностей без онбординга | Отток до первой победы | Тест новичков: доехать и выстрелить за N минут |
| Физика «рандомная», не читаемая | Нет обратной связи / хаос joints | Несправедливость, злость | Playtest: игроки объясняют причину поражения |
| PvP не converging | Слишком сильные эксплойт-сборки | Мёртвая мета | Серия боёв + запрет/лимиты brackets |
| Damage неинтересный | Только полоска HP | Потеря identity | Сравнение «HP-only» vs component disable |
| Сеть ломает fun физики | Desync, rubberbanding | Неиграбельный core | EXP-05…EXP-09 в [UNITY_ENGINE.md](UNITY_ENGINE.md) |
| Экономика убивает креатив | Силовые unlocks | Pay/grind to win | Не включать в MVP; A/B позже на отдельном режиме |
| Контентный creep | Давление «добавить ещё пушку» | Размытие глубины | Лимит типов деталей до стабилизации систем |
| Нет фантазии «я автор машины» | Слабый configure | Ощущение обычного arena fighter | Опрос: «чем ваш робот уникален?» |
