==================================================
PROJECT
==================================================

**Рабочее название:** `ra2-analog`

**Репозиторий:** https://github.com/Nadomas/ranalog-ra2.git

**Рабочее описание:**

Современный духовный наследник Robot Arena 2.

Игра про конструирование боевых роботов, программирование их управления, физическое тестирование и последующие физические бои.

Главная ценность игры находится не в количестве контента, а в глубине систем и свободе инженерного проектирования.

Игрок должен чувствовать себя:

- инженером;
- конструктором;
- разработчиком системы управления;
- тестировщиком;
- пилотом/тактиком.

**Ключевая фантазия игрока:**

«Я сам спроектировал машину, сам придумал, как она должна работать, сам настроил её управление, протестировал гипотезу и отправил её против другого игрока.»

==================================================
REFERENCE
==================================================

Главный концептуальный референс — **Robot Arena 2**.

Нельзя ограничиваться копированием визуального стиля или идеи «роботы дерутся».

Главное наследуемое свойство Robot Arena 2:

Игрок не просто выбирает готового робота.  
Игрок **создаёт систему**.

Конструкция робота, расположение компонентов, механические связи, управление и поведение в бою — взаимосвязанные части одной системы.

Особенно важно сохранить:

**DESIGN ≠ CONFIGURE**

Сначала игрок физически проектирует робота.  
После этого он отдельно проектирует систему управления.

Игра должна позволять множество разных решений даже при одинаковом наборе деталей.

---

==================================================
CORE DESIGN PILLARS
==================================================

1. **ENGINEERING** — инженерные решения, а не «статистически лучший предмет».
2. **FREEDOM OF CONSTRUCTION** — можно строить необычные и плохие конструкции; не душить игрока ради простоты реализации.
3. **CONTROL PROGRAMMING** — управление — отдельная полноценная система.
4. **PHYSICS** — физика = core gameplay; свойства конструкции реально влияют на поведение.
5. **FAST ITERATION** — идея → конструкция → настройка → тест → ошибка → правка → снова тест.
6. **MULTIPLAYER-FIRST** — сеть учитывается с начала, не «потом прикрутим».
7. **SKILL-BASED PVP** — преимущество из конструкции, управления, тактики и навыка; не pay-to-win и не обязательный power-progression в competitive PvP.
8. **DATA-DRIVEN** — компоненты, actions и значимая часть правил — данными; новая деталь без переписывания всей архитектуры.
9. **TESTABILITY** — опасные гипотезы проверяются экспериментами; нет уверенности теоретически → `[EXPERIMENT REQUIRED]`.
10. **MINIMAL CONTENT, DEEP SYSTEMS** — глубина construction + physics + controls + damage + multiplayer важнее каталога контента.

==================================================
CORE GAMEPLAY LOOP
==================================================

```
DESIGN → CONFIGURE → TEST → BATTLE → RESULTS → DESIGN
```

Локальная быстрая петля:

```
DESIGN ↔ CONFIGURE ↔ TEST
```

должна быть максимально короткой (желательно бесшовной).

Этот цикл — фундамент игры.

---

==================================================
1. DESIGN
==================================================

Игрок создаёт робота как **физическую систему**, а не выбирает пресет.

Возможные действия (концептуально):

- границы / форма корпуса;
- материалы;
- размещение компонентов (двигатели, колёса, оружие, приводы, батареи и т.д.);
- соединения и механические отношения;
- учёт массы, центра масс, мощности, физических ограничений.

Архитектуру нельзя строить вокруг заранее созданных фиксированных роботов.

---

==================================================
2. CONFIGURE
==================================================

После конструкции игрок настраивает управление.

Каждый тип компонента предоставляет **actions** (data-driven).

Примеры:

| Компонент | Actions |
|-----------|---------|
| Rotor | rotate_forward, rotate_backward, brake, lock/stop |
| Piston | extend, retract, stop |
| Wheel | forward, reverse, steering_left, steering_right |
| Weapon | activate, deactivate |

Actions назначаются на input. Система должна быть гибче пресета WASD.

### GROUPS

Компоненты объединяются в группы. Группы дают **composite actions**.

Пример — четыре колеса → группа DRIVE → танковое руление на WASD.

Конкретную схему WASD **нельзя** жёстко зашивать в код как единственную модель управления.

---

==================================================
3. TEST ROOM
==================================================

Одна из ключевых систем. Задача — максимально быстрый iteration loop.

Игрок должен ходить Design ↔ Configure ↔ Test без ощущения «запуска отдельной игры» и без долгих загрузок.

Test Room: движение, управление, оружие, механика, физика, быстрый reset, повтор, поиск ошибок конструкции.

Допустимы внутренние debug-инструменты даже если они не попадут игроку.

Тот же robot blueprint / та же базовая физическая модель, что пойдут в бой.

---

==================================================
4. BATTLE
==================================================

Физические бои. Перспективный фокус — **PvP**.

Возможные форматы (набор **не** фиксирован): 1v1, FFA, elimination, tournament, timed, team, experimental.

Бой использует **ту же базовую физическую модель**, что и Test Room.  
Не делать отдельную «фейковую» PvP-физику.

---

==================================================
5. RESULTS
==================================================

После боя игрок получает разбор, достаточный чтобы вернуться в Design с гипотезой.

Минимум по смыслу: исход и причина; урон; затронутые компоненты; длительность / ключевые отказы.

Results — часть loop, не отдельный «экран очков ради очков».

---

==================================================
FIXED DECISIONS
==================================================

Договорённости, которые агенты и люди считают **принятыми**, пока продукт явно не пересмотрит:

| Решение | Статус |
|---------|--------|
| Production engine = **Unity** | Зафиксировано |
| Unreal / другие движки как production | Вне scope |
| Multiplayer-first + physics-first + data-driven | Обязательные принципы |
| Design и Configure — разные фазы | Обязательно |
| Competitive PvP без pay-to-win / обязательного power-progression | Обязательно |
| Economy / career | **Не** часть core MVP loop; отдельный опциональный слой позже |
| Опасные tech-решения | Только после эксперимента (`[EXPERIMENT REQUIRED]`) |
| Critical path risk | Сначала доказать **physics + multiplayer**, потом наращивать редактор/контент |

Конкретные Unity packages, physics stack, netcode, dedicated server details, serialization — **не** считаются зафиксированными без эксперимента (см. `docs/UNITY_ENGINE.md`).

---

==================================================
HARD CONSTRAINTS / NON-NEGOTIABLES
==================================================

1. Не проектировать «одиночную игру с уникальной моделью робота, сеть потом».
2. Не подменять engineering fantasy пресетами готовых роботов как единственным путём.
3. Не делать Design и Configure одной неразличимой кашей без отдельной системы actions/bindings/groups.
4. Не жертвовать Fast Iteration ради «правильной» длинной загрузки между правкой и тестом.
5. Не вводить в competitive PvP обязательную силу через grind/pay.
6. Не раздувать контент раньше стабилизации core-систем.
7. Не принимать неподтверждённые physics/net решения «потому что так принято в туториалах».
8. Не пропускать проверку главного риска: локально красивая физика может оказаться непригодной для PvP-синхронизации.

---

==================================================
MULTIPLAYER CONTEXT (STABLE)
==================================================

- Целевая модель боя: **server-authoritative** simulation.
- Клиент: input + presentation (и только осторожный prediction после доказательств).
- Robot loadout (blueprint + control map) должен уметь валидироваться и приниматься на сервере.
- Test Room может быть локальным, но формат робота — тот же, что для матча.
- Lobby / session / results — часть долгосрочного MP-пути; ранний spike может быть тонким, но контракты данных MP-aware.

Детали подходов (snapshots, prediction, proxies) — в SDS / экспериментах; здесь фиксируется только принцип authority и early risk proof.

---

==================================================
PHYSICS CONTEXT (STABLE)
==================================================

Физика — не декорация.

Концептуально учитывать: rigid bodies, collision, joints, mass, CoM, motors/torque, силы, повреждения, потенциальный detach.

MVP-ориентир по договорённостям review: читаемые **функциональные отказы** частей важнее раннего полного debris/detach в сети.  
Истинный detach в net — только после экспериментальной валидации.

---

==================================================
MVP SPIRIT (NOT A FEATURE LIST)
==================================================

MVP должен уже быть **Robot Arena-like**:

собрал → настроил управление (включая groups/composites) → быстро протестировал → сразился физически (в т.ч. путь 1v1/online) → понял результат → вернулся улучшать.

MVP **не** обязан иметь: экономику, большой каталог, много режимов, spectator/replay product, pay progression.

---

==================================================
EXPERIMENTATION RULE
==================================================

Если нельзя уверенно выбрать решение теоретически:

1. Пометить `[EXPERIMENT REQUIRED]`.
2. Сформулировать гипотезу, метод, метрики, success/fail.
3. Записать результат (см. `docs/experiments/`).
4. Только потом фиксировать архитектурный выбор.

Критический класс экспериментов: runtime modular robot, many bodies/joints, two-robot interaction, damage/detach, net physics sync, authority, input sync, latency, dedicated server.

AI / MULTI-AGENT RULES
==================================================

При работе любого агента над этим репозиторием:

1. Сначала читать **этот файл** как стабильный контекст.
2. Не противоречить pillars и Fixed Decisions без явного запроса человека на пересмотр.
3. Для деталей геймдизайна → `docs/GDD.md`.
4. Для «как реализовать» → `docs/SDS.md`.
5. Для порядка доказательств и gates → `docs/TECHNICAL_ROADMAP.md`.
6. Для Unity/experiments → `docs/UNITY_ENGINE.md`.
7. Для известных архитектурных рисков → `docs/ARCHITECTURE_REVIEW.md`.
8. Не выдумывать финальные числа, win conditions, package choices и net strategy, если они помечены open / experiment.
9. Не предлагать смену production engine на Unreal/Godot, пока product lock на Unity не снят явно.
10. Предпочитать маленькие проверяемые шаги огромным незадокументированным подсистемам.
