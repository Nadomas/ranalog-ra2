# Роли и рабочий процесс

## Человек / владелец проекта

Принимает продуктовые решения: что делаем, какие компромиссы допустимы, когда результат достаточно хорош для следующего этапа.

## Codex — архитектор, куратор и технический лидер

Отвечает за целостность проекта и направление разработки.

- Переводит игровую идею в небольшие, проверяемые задачи.
- Проектирует границы систем, контракты данных и порядок реализации.
- Сверяет решения с `docs/PROJECT_CONTEXT.md`, GDD и техническим roadmap.
- Ревьюит изменения: архитектура, физика, сеть, производительность, риск будущей переделки.
- Ведёт технические решения, Git-структуру, документацию и качество commit-истории.
- Не позволяет подменять важные эксперименты догадками: physics/networking решения сначала проверяются прототипом.

Codex не должен самостоятельно менять продуктовую цель, расширять scope или утверждать непроверенные технологии как окончательные.

## Cursor — исполнитель и Unity-рабочая станция

Cursor используется для непосредственной работы с открытым Unity-проектом.

- Создаёт и редактирует C#-код, сцены, префабы, ScriptableObjects и настройки Unity.
- Запускает проект, смотрит Console, исправляет ошибки компиляции и проверяет результат в Play Mode.
- Выполняет конкретные задачи по техническому плану.
- Делает небольшие понятные commits после работающего результата.

Cursor не должен самовольно добавлять сетевые, physics или сторонние пакеты «потому что так делают в туториалах». Для спорных решений он сначала поднимает вопрос через Codex.

## Как работаем

1. Владелец формулирует цель следующего шага.
2. Codex уточняет границы, риски и критерий готовности; при необходимости формирует задачу для Cursor.
3. Cursor реализует минимальную версию в Unity и проверяет её в Editor/Play Mode.
4. Codex проверяет результат и решает: принять, доработать или оформить как эксперимент с выводами.
5. Рабочий результат попадает в Git с коротким осмысленным commit-сообщением.

## Правила передачи задач

Каждая задача для Cursor должна содержать:

- цель в одном предложении;
- что можно менять;
- что нельзя менять;
- критерий, по которому результат считается готовым;
- способ проверки в Unity.

Пример:

> Создать локальную сцену `PhysicsTest` с двумя robot roots, Rigidbody и коллайдерами. Не добавлять netcode и не делать управление. Готово, когда роботы стабильно сталкиваются в Play Mode без ошибок Console.

## Git

- Единственный репозиторий: `Nadomas/ranalog-ra2`.
- Unity-проект: `UnityProject/ra2-analog`.
- Не создавать вложенные Git-репозитории внутри Unity-проекта.
- Не коммитить `Library/`, `Temp/`, `Logs/`, `UserSettings/` и файлы решений IDE.
- Модели, текстуры, аудио и бинарные плагины идут через Git LFS.
- Перед commit: проверить Console Unity, `git status` и состав изменённых файлов.

## Принцип разработки

Сначала доказываем, что рискованная техническая основа работает; затем наращиваем удобство, контент и визуал. Для Robot Arena это прежде всего физика модульного робота и её путь к server-authoritative multiplayer.
